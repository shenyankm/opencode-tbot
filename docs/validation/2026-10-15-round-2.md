# Shutdown and durable cancellation — 2026-10-15

This iteration builds on `471e225` from [round 1](./2026-10-15-round-1.md). Mobile and physical desktop button acceptance remain open. Package version remains `0.2.0`; these changes are unpublished.

## Reproduced problems

1. Stopping polling left foreground controllers live and their session mappings retained. Two runtime regressions demonstrated missing cancellation and container disposal occurring before an already-started runner stop had finished.
2. A real isolated OpenCode `2.0.29` host durably admitted an input with `resume: false`. Cancelling its foreground request ended the local wait but left the input in the inbox. The updated integration test failed before the patch and passed afterward.
3. A separate status query cannot establish whether execution is active when the subsequent interrupt reaches the server. An idle snapshot also skipped interruption when pending input could have been delivered in the meantime. V2 interruption already reports whether it interrupted an active execution and treats idle execution as a no-op.

## Smallest complete changes

- Close the foreground tracker before stopping polling: abort preparing and executing leases, clear request/session mappings, and reject new acquisitions. Direct container disposal also closes the tracker.
- Wait for the existing stop Promise when `stop()` and `dispose()` overlap. The regression checks that container disposal occurs only after that Promise resolves.
- Cancel the foreground request's original inbox ID before interrupting execution. Recheck request identity after the cancellation response so a replacement request is preserved. Failure still aborts the captured local lease and propagates the remote error.
- Use the V2 interrupt response directly, eliminating the status preflight and reducing the cancellation use case from 107 to 70 lines. Existing result statuses and the busy/idle compatibility field are derived from that authoritative boolean response.
- Bound inbox cancellation using the existing poll-request deadline. No new config, dependency, command, or translation key is required. The three READMEs and Unreleased changelog describe cancellation and reload behavior consistently.

The shutdown change cancels local request signals and tracked SDK waits; it does not issue a session-wide interrupt or delete shared sessions during reload. Server execution remains owned by OpenCode. These tests do not prove that every already-started external preprocessing operation terminates immediately on reload.

## Reproducible request-count comparison

Compare the baseline cancellation use case from Git commit `4693c08` with the updated implementation. Use one chat lease, a repository bound to `previous`, a stub status endpoint reporting `previous` busy, and an interruption endpoint returning `true`. Count endpoint calls, asserting both implementations abort the local signal. In the executing fixture attach the lease to `previous` before cancelling; in preparation leave it unattached. No inbox ID is attached in this comparison so it isolates removal of the status preflight.

| Fixture | Baseline calls | Updated calls |
| --- | ---: | ---: |
| Cancel preparation with an older bound busy session | 2 | 0 |
| Cancel an attached running session | 2 | 1 |

The second fixture removes one status round trip while retaining interruption. Cancellation with a known inbox ID adds the required targeted cancellation operation. This is an endpoint-count improvement, not a measured claim about general Telegram latency or throughput.

Local diagnostic output is under ignored `.codex-e2e/round2-package/` and `/tmp/opencode-tbot-round2-*.log`. The inbox regression runs through the committed host test. The baseline request-count comparison is stored in `cancel-overhead.json`; no credentials are stored in these artifacts.
